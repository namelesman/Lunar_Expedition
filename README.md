# Lunar Landing Site Navigator

NASA Space Apps Challenge 2026 — challenge
[*Lunar Landing Site Navigator*](https://www.spaceappschallenge.org/2026/challenges/lunar-landing-site-navigator/).
Team from Recife, Brazil.

**Live app: <https://lunar-expedition.vercel.app>**. The submission text (summary, use of AI,
NASA data) is in [`docs/submission.md`](docs/submission.md).

A web app to compare lunar landing sites and dates in seconds. For each site it shows:

- where the **Sun** and the **Earth** are relative to the **real terrain horizon**;
- how long until sunset and Earthset;
- the power and direct-to-Earth communication windows over the coming weeks.

All of it sits on a real-time 3D Moon built from NASA LRO data.

## Features

- **Sites:** 15 curated landing sites (Apollo, CLPS, other agencies, Shackleton), each with its
  official source, plus any custom coordinates. A double-click on the Moon adds a point too.
- **Sun and Earth vs the terrain horizon:** a LOLA horizon at 720 azimuths, up to 300 km.
  - Current elevation and visible share of each disk.
  - Countdown to sunset or sunrise, and to Earthset or Earthrise.
  - A 360° local-sky panorama with the 30-day tracks.
- **Next 30 days:** sunlight, Earth-visibility and both-at-once windows, the Sun's elevation vs the
  terrain, the longest night and the longest communication gap.
- **Next 12 lunations:** polar seasons and libration, lunation by lunation.
- **Solar energy at a panel:** mean W/m² and kWh/m² over 30 days, for a vertical panel facing the
  Sun and for a flat one.
- **Sunlight and Earth-visibility map** of the 20 × 20 km around a site, computed in your browser:
  - best-spot table;
  - "shadows now" view;
  - click a spot to open it as a new site.
- **Compare** up to three sites side by side.
- **Time controls:** pick any date and time, or play the month.
- **Real sky:** the Sun and Earth at their true positions and sizes, the Earth's phase, and the
  NASA star map.
- **Help and glossary**, phone layout, no account, no cookies, no analytics.

See [`docs/challenge.md`](docs/challenge.md) for the official objectives and how each one maps to
the app.

## Repository layout

```
apps/web/        Next.js (App Router) + TypeScript: UI, 3D globe, Web Worker for terrain (static, no server code)
packages/core/   Pure, tested logic: types, coordinates, Sun/Earth ephemeris, terrain horizons, DEM tiles,
                 sunlight map, lunations
scripts/         Node + TypeScript data pipeline (GLB optimization, horizon masks, DEM tiles, sky textures)
data/            sites.json (curated landing sites with official sources)
docs/            Challenge summary and submission text
```

Raw NASA files (TIFF/EXR/GLB) and generated tiles are **never committed**; the scripts in
`scripts/` download and regenerate everything.

## Quick start

```bash
npm install
npm run dev        # http://localhost:3000
npm test           # unit tests (packages/core)
npm run check      # typecheck + tests + production build
```

### Data pipeline (Node + TypeScript, `scripts/`)

Everything runs on Node 22+ with `tsx`; no Python. Raw NASA files go in `data/raw/` (git-ignored).

```bash
npm run glb:optimize -- path/to/Moon_NASA_LRO_8k_Topo.glb apps/web/public/models   # SVS #14959 → web GLBs
npm run glb:fit -w @lunar/scripts      # calibrate the GLB against LOLA (needs data/raw/svs-4720/ldem_16_uint.tif)
npm run data:horizons                  # horizon masks per site (needs ldem_64_uint.tif)
npm run data:dem-tiles                 # LOLA DEM tiles for browser horizons (--download fetches the rasters)
npm run data:fixtures                  # albedo fixture for the core tests
npm run sky:textures                   # star map (SVS #4851 starmap_2020_8k.exr) + Earth (Blue Marble NG)
npm run assets:stage                   # stage models + sky for the static assets project
```

Heavy web assets (optimized GLBs, star map, DEM tiles) are git-ignored and served from a separate
static Vercel project (`NEXT_PUBLIC_ASSETS_BASE_URL`); `npm run assets:stage` then
`vercel deploy --prod` in `data/cache/assets-site` publishes them. The GLBs and the star map are
uploaded (~15 MB). The DEM tiles (~0.6 GB, 8,800 files) are generated by that project's build: it
downloads the NASA rasters, checks their SHA-256 and runs the bundled `dem-tiles` script. A Vercel
Hobby CLI upload is capped at 100 MB, but files a build creates are not.

### Terrain horizon for custom points (computed in your browser)

Curated sites use precomputed masks (`apps/web/public/data/horizons.json`). For any other point
(typed coordinates or a double-click on the Moon) a Web Worker downloads only the LOLA tiles that
point needs and runs the **same** `horizonMask` (`packages/core/src/terrain.ts`): 720 azimuths,
terrain marched to 300 km with exact curvature, observer 2 m above the ground. There is no server
code. If a tile fails or nothing comes back within 15 s, the point keeps a smooth-sphere horizon
and the panel says so.

| Band | Layer (finest first) | Source | Resolution |
| --- | --- | --- | --- |
| ≤ 50 km | `polar-s-80m` (≤ 80°S) | LOLA GDR LDEM_80S_80M | 80 m |
|  | `ldem-64-n` (≥ 85°N) | ldem_64 resampled to a polar grid | 118 m |
|  | `ldem-64` | CGI Moon Kit ldem_64, 5° tiles | 64 px/° (≈474 m) |
| 50–300 km | `polar-s-960m` (≤ 75°S) | LDEM_75S_120M, 8×8 mean | 960 m |
|  | `ldem-16-s` / `ldem-16-n` (|lat| ≥ 60°) | ldem_16 resampled to polar grids | 948 m |
|  | `ldem-16` | CGI Moon Kit ldem_16, 30° tiles | 16 px/° (≈1.9 km) |

Near the poles, equirectangular tiles are mostly redundant columns, and a 300 km radius spans
every longitude. The polar grids keep every site within budget: ≤ 4.1 MB per site over all
probes, including both poles.

Validation (`packages/core/test/demTiles.test.ts`, run after `npm run data:dem-tiles`):

- Tiles are lossless. Through the tile path, ldem_64 reproduces `horizons.json` exactly
  (Apollo 11, IM-1, IM-2, Shackleton). Every layer is also re-read from its tiles and must be
  bit-identical to the full raster.
- The coarser 50–300 km layers change the horizon by at most 0.046° (IM-1; RMS 0.003°). They do not
  change it at Apollo 11, IM-2 or Shackleton.
- South of 80°S the app uses the 80 m LOLA DEM for the first 50 km. It resolves relief that ldem_64
  smooths, so it differs from `horizons.json` by up to 2.7° (IM-1), 1.6° (IM-2) and 0.7°
  (Shackleton). Those differences are real terrain, not an error.

Measured in the browser (Chromium, cold cache, tiles from the production assets host over HTTPS,
16 parallel requests):

| Point | Downloaded | Tiles | Time to horizon | of which the march |
| --- | --- | --- | --- | --- |
| Equatorial 8.5°N 31.4°E | 2.0 MB | 7 | 1.1 s | 0.3 s |
| South polar 89.45°S 137.31°W | 3.3 MB | 126 | 2.7 s | 0.4 s |
| North polar 86.2°N 40°W | 3.7 MB | 89 | 2.1 s | 0.4 s |

Tiles stay in the worker's memory, so a nearby second point downloads little or nothing.

### Sunlight and Earth-visibility map around a site (on demand, in your browser)

The site panel can map the 20 × 20 km around any site, so a planner can see whether a better-lit or
better-connected spot sits a few kilometres away. The button starts a job in the same Web Worker
(`packages/core/src/illumination.ts`):

1. It downloads the LOLA tiles for two local grids in an azimuthal-equidistant projection centred on
   the site: ±60 km at 100 m (near field) and ±310 km at 1 km (far field). It uses the same layer
   stacks as the horizon above.
2. It computes the terrain horizon of each of the 41 × 41 cells (every 500 m) at 180 azimuths. Each
   cell is marched to 300 km with the same observer height (2 m) and exact curvature as
   `horizonMask`.
3. On the main thread, it counts the 30-minute samples of the current 30-day window during which
   the centre of the Sun, and of the Earth, is above each cell's horizon. This is the same criterion
   as the panel's "sunlit" and "Earth visible" shares. Moving the window recomputes this step
   instantly, with no new download.

Layers: **Sun · 30 days**, **Earth · 30 days**, and **Shadows now** (lit or shadowed at the selected
time; play the clock to watch the shadows move). Relief shading sits underneath. You can hover any
cell for its values, and click a cell (or a row of the "best spots" table) to open it as a custom
point with its own full analysis.

Validation (`packages/core/test/illumination.test.ts`, synthetic terrain, and
`packages/core/test/demTiles.test.ts`, real tiles):

- On synthetic hills and pits (south polar and equatorial), every tested cell's horizon matches
  `horizonMask` run at that cell's own coordinates within 0.3°. The tested cells are the centre,
  the corners, and cells off the axes; near the pole this includes grid convergence.
- A cell's sunlit and Earth-visible shares equal `computeConditions` with that cell's horizon,
  within 3 of 1441 samples.
- With real tiles, the centre cell's horizon matches the site horizon computed by the browser
  path within 0.012° (Apollo 11) and 0.154° (Shackleton).

Measured (Node for the computation, headless Chromium for the download from the production assets
host, cold cache):

| Site | Downloaded | Tiles | Horizons of 1,681 cells |
| --- | --- | --- | --- |
| Apollo 11 (0.67°N 23.47°E) | 2.2 MB | 8 | 2.7 s |
| Shackleton (89.67°S 129.78°E) | 4.5 MB | 175 | 3.1 s |

At Shackleton the map shows the floor of the crater in permanent shadow (0 %) and the rim lit up
to 96 % of the window, 10 km from the centre. At Apollo 11 the mare is flat: 47–49 % everywhere.

### Next 12 lunations (seasons)

The site panel also charts the sunlit and Earth-visible share of each lunation, new Moon to new
Moon, for the lunation of the analysis window and the 12 after it
(`packages/core/src/seasons.ts`). It uses 2-hour samples against the same terrain horizon, about
4,400 sky states, computed once in about 150 ms. Near the poles the Moon's 1.54° axial tilt makes a
polar summer and winter, and libration moves the Earth by up to about 7°. A site that looks good
in one 30-day window can therefore be poor six months later.

Examples, starting from the November 2026 lunation:

- IM-2 (Athena) is sunlit 36–53 % of the time depending on the lunation, with the Earth visible
  74–84 %. Its longest night is 19 days.
- Apollo 11 stays at 49–50 % sunlight, with the Earth always up.

Click a column to move the 30-day analysis window to that lunation.

Tests (`packages/core/test/seasons.test.ts`):

- Lunations are contiguous synodic months; the new Moon of 2026-11-09 is found within 10 minutes.
- An equatorial site is sunlit 46–54 % of every lunation, with nights of 14–15.5 days.
- At 89.67°S the smooth-sphere sunlit share swings between more than 90 % and less than 10 % over
  the year.
- Every share equals `computeConditions` over the same samples.

### Solar energy at a panel

The site panel estimates the sunlight that reaches 1 m² of solar panel over the 30-day window
(`packages/core/src/energy.ts`), before cell efficiency, dust or temperature:

- irradiance = 1361 W/m² (total solar irradiance at 1 AU, Kopp & Lean 2011) × (1 AU / Sun
  distance)², with no atmosphere to cross;
- times the share of the Sun's disk above the terrain horizon;
- times the cosine of the angle between the Sun and the panel's normal: cos(elevation) for a
  vertical panel turned to face the Sun, sin(elevation) for a flat panel on level ground.

Averages include the night. Examples for the window starting 2026-11-14:

- IM-2 (84.8°S): 726 W/m² on a vertical panel but 58 W/m² on a flat one, because the Sun stays
  low.
- Apollo 11 (0.7°N): 437 W/m² on either panel, close to 1361 / π.
- Shackleton crater floor: 0 W/m² (permanent shadow).

Tests (`packages/core/test/energy.test.ts`):

- The 1/r² scaling holds, and the Sun–Moon distance stays within 2 % of 1 AU.
- At the equator, both panels average 1361 / π within 5 % over two lunations.
- Near the pole, a vertical panel gets the sunlit share of the full flux and more than 10 times
  what a flat one gets.
